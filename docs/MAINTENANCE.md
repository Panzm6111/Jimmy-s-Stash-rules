# 当前维护流程

日常只使用两份最新主订阅：[Stash](../config/stash.yaml)、[Clash](../config/clash-verge-auto.yaml)。旧Windows任务登记已移除，安装脚本、旧自动发布程序及其专属测试已删除，不再重新安装电脑定时任务。

## 自动执行

每端23份兼容规则由客户端直接订阅上游，24小时尝试刷新（合计24个不同地址）。6份必要转换由[必要规则云端更新](../.github/workflows/refresh-rules.yml)每天北京时间12:17计划执行，也可在Actions页面手动运行。GitHub调度可能延迟，长期无活动可能停用，不能承诺准点。

云端只检查核准来源、许可、语法与变化量，生成并运行回归后精确提交。未知格式、许可变化、大差量或验证失败停止发布；没有实际变化不提交。私人机场和节点不进入这个流程。普通后续维护仍使用正常Git提交，不对每日任务启用强制推送。

每天还运行`tools/verify_subscriptions.py`，读取24份直订上游，检查HTTP、格式、空集及相对已审查快照的变化量，并使用本次真实下载内容检查两端75组代表性App/评论/游戏域名URL。移除超过10%、总变化超过25%或超过5000条，沿用现有差量门槛进入人工审查；该门槛是报警条件，不证明上游维护差。基线只在人工审查后更新，不自动接受异常。公开主配置推送时的CI也执行同样检查。

无变化也会产生带UTC检查时间的Actions Summary和`public-subscription-health`附件，保存30天；只上传两份明确指定的公开健康报告，不上传整个.local、原始节点或私人URL。不为时间戳制造Git提交。失败使工作流失败并停止本轮转换发布；客户端仍直订上游，此监测不能冻结或回滚设备已下载的规则。

通知使用GitHub Actions原生失败通知，是否收邮件/站内通知取决于账号的Actions通知设置，仓库代码无法替用户保证开启。到GitHub Settings → Notifications → Actions确认接收失败工作流通知。计划未启动时无法依靠同一个计划自报故障；查最近一次成功运行时间，而不是最后一次规则提交时间。未额外建立电脑任务或外部告警服务。

## 项目开发

维护源、模块、规则快照、许可证和测试是生成当前两个入口所需内容，不是旧发布版本。功能修改后运行对应生成器和现有验证：

```text
python -X utf8 tools/build_ads.py
python -X utf8 -m unittest discover -s tests -p "test_*.py" -v
python -X utf8 tools/validate.py
```

Windows使用项目`.venv`内的Python并启用UTF-8；JS验证还需要Node。全库检查应在仅含受控文件的隔离副本执行，避免读取`.local`内的私人备份。上游专项HTTP/JS和Adobe官方补充仍需人工审查，不盲目整包覆盖。

保留`PROGRESS.md`为唯一状态主文件，每次重要变更原位记录证据和未验收边界。需求和沟通过程、历史研究数据继续保存；源码删减前先核对实际生成/导入依赖。详情见[协作入口](../AGENTS.md)、[来源](SOURCES.md)和[更新说明](UPDATES.md)。
