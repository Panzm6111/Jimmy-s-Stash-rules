# 去广告模块、覆盖状态与安全恢复

核实：2026-10-19。**没有 iPhone 广告效果实测通过记录**。当前通过的是来源、许可、代码范围和模拟测试，不是所有 App 去广告。

## 针对“淘宝、微博开屏仍在，几乎所有 App 无效”的修订

已记录用户实际反馈为**效果不合格**；HTTP/MITM及设备证书状态还未知，不把失败归咎于用户操作。这次查到的是本地适配缺陷与覆盖遗漏：

- 基础广告由21条增加到38条，补上穿山甲、百度、广点通、Unity Ads的已收录域名/关键词。保持人工选择，不自动启用38,066条大包或`umeng`宽匹配。
- 淘宝补齐专用`taobao-splash`条目的缺省控制字段，兼容已有数字/布尔类型；小红书补齐明确广告记录的展示时间。旧适配要求字段已存在，可能什么都没改。
- 微博两个开屏端点改在请求阶段返回`200 + {}`，不再等服务器返回成功JSON。脚本也兼容原来已导入的响应式模块；只刷新JS不会把旧配置变成新请求式配置。
- 另有16条端点改用原生请求脚本，恢复上游空JSON/空200的处理意图：大麦、高德、麦当劳、脉脉、猎聘、米家、网易邮箱、网易云音乐、闲鱼、小宇宙、WPS、知乎。仍需手机验证，不能据此保证当前App接受此响应；网易云加密接口尤其需要实测。
- 联通两条来源为`reject-img`，目前仍是普通拒绝，未实现等价空图片。肯德基/航旅的素材拦截可能保留空白倒计时；美团模块只有外卖端点，WPS/携程部分规则只是统计；B站未覆盖protobuf，独立天猫没有专项。详见目录，不能把40个模块写成40款已去广告。

### 已安装用户怎么更新

**先保留现在能上网的配置，在设备创建备份；不要重新填写订阅或重新生成证书。**

1. 如果当前使用从GitHub订阅的`config/stash.yaml`，刷新这一原地址；只在私人订阅已放入独立本地覆写时这样做。如果直接在主配置里填过机场URL，先备份并保留该字段，远程刷新会覆盖它。
2. 如果使用逐款广告覆写，刷新原来已添加的对应覆写，不重复添加；再刷新脚本资源。本次微博及16条端点需要**配置和JS都更新**。一体化主配置已包含同款处理，不再叠加这些模块。
3. 如果使用没有远程来源的本地私人文件，它不会自动获取新的规则或handler；仅远程JS可单独刷新，淘宝/小红书和旧响应式微博可先得到脚本修正。不要用含占位符的公共配置直接覆盖这个能用的私人文件。要获取全部本轮变更需在本地重新合成/合并，见[私人文件说明](SUBSCRIBE.md#已有完整机场文件合成一个本机导入文件)（如使用构建工具，输出始终留在仓库外）。
4. 检查脚本下载成功，并确认下方HTTP/MITM及自建证书信任已完成。然后退出淘宝、微博并重新打开，各测试一次开屏和正常浏览。不要求卸载App或进行付款测试。

本轮完整新配置识别：**38条基础广告，12份脚本，18个请求handler＋10个响应handler，16条拒绝重写，41个精确MITM主机**。这是部署识别，不是有效率指标。配置、规则、脚本的更新机制不同；旧内嵌规则不会随JS刷新而改变。

### 用固定日志判断运行到哪一步

在Stash脚本运行日志中搜索`[JimmyAds]`（具体日志入口随版本变化）。只反馈如下固定行和App名称/版本，不发送完整网络日志、完整URL、Cookie或请求正文。

| 标记 | 含义与下一步 |
|---|---|
| `[JimmyAds][taobao] changed`、`[JimmyAds][xiaohongshu] changed` | 脚本识别并修改了响应；若仍有广告，需要核对缓存或其他广告链路，不能继续盲加域名 |
| `unchanged` | 命中接口，但没有需要改变的已知字段，或数据已处理 |
| `unsupported-schema` / `unsupported-body` | 命中了，但数据结构/类型/大小或JSON解析不符合处理条件；原样放行 |
| `http-error` | 响应状态不接受，或状态格式未识别；不是确定的账号过期结论 |
| `[JimmyAds][weibo] changed` | 微博新请求式空JSON或旧响应式空JSON已产生；只有同时更新模块才是请求式 |
| `[JimmyAds][具体模块] empty-json` / `empty-200` | 新的专用广告请求已返回空响应 |
| 完全没有标记 | 不能直接判定“规则过时”：先确认JS版本/下载和日志入口，再查模块启用、MITM以及实际接口是否命中 |

这些日志只有固定模块名和状态，不含URL、正文、头部或异常文本；不上传、不存储账号、不推送通知。`changed`只证明脚本产生修改，不证明Stash已采用修改或广告已经消失。HTTP/非443端点、HTTP/3、证书固定与App改接口仍有缺口；当前没有为所有HTTP端口强制处理，也没有全域解密。

## 分层与优先级

基础包默认参与分流，较少且明确的域名优先；扩展包含更多共享追踪、广告关键词与 IP，单独导入即可启用。扩展模块只替换“基础广告”规则集的来源 URL，沿用核心中的同一条广告规则，不向规则列表最前方插入广告。这样局域网、系统通知和指定登录/更新例外始终优先。已验证 38 条基础规则均包含在扩展包中；两份快照不会同时执行，各快照内部已去重。不要再叠加来源不明的“全能去广告包”。

广告SDK也可能提供用户主动观看的奖励视频；需要看广告才能领券的流程会受到域名阻断影响。普通领券业务没有被直接屏蔽，但不能承诺依赖广告的流程正常。三条DOMAIN-KEYWORD按主机名子串匹配，误杀用精确主机白名单恢复。

本机白名单置于最前，覆盖误杀；基础/扩展通过同一规则位置指向“广告拦截”组。选 `DIRECT` 可同时放行这些域名。**HTTP重写与响应脚本另有开关**，不会随该组改 DIRECT 停止。

本地共有40个App专项和1个扩展包；图片中39款有专项。完整结构预期为18条请求handler、10条响应handler、16条HTTP拒绝重写、41个去重后的MITM主机，不建议整包开启。每个模块、正反序全量及所有有序模块对均检查过期望合并；端点没有重复匹配。实际Stash数组合并仍需预览核对，不能只保留最后一个。全部导入地址、精确主机与原通用规则的重叠见[模块目录](AD-MODULES.md)。

## MITM 的作用和步骤

HTTPS 原本由 App 与服务器加密；Stash 需要用你设备生成的受信任 CA，在匹配的精确域名上解密并处理明确广告请求或修改响应。信任 CA 会让 Stash 能看见这些域名的内容，**虽然脚本只改路径，域名层解密范围仍是整个该域名**。不愿意接受这个范围时，不启用相应模块；基础域名拦截不需要 CA。

1. 先看 [Stash 能力来源](STASH-CAPABILITIES.md)，使用当前版本官方指引核对菜单。
2. 在 Stash 的 HTTP/MITM 设置中本机生成 CA，按它的提示在 iOS 安装描述文件。
3. iOS“设置 → 通用 → 关于本机 → 证书信任设置”，仅完全信任你刚生成的 Stash CA。不要安装别人发来的 CA。
4. 在 Stash 开启 HTTP/MITM，并单独启用一个广告覆写。不要添加 `*`、`*.com` 或银行支付域名；不要配置跳过上游证书校验。
5. 彻底退出目标 App 后重新打开，验证登录、消息、正常内容、播放、领券（如适用）。缓存广告不一定马上消失，不建议为去广告反复卸载导致登录数据丢失。
6. 保留 CA 私钥在设备；导出用于备份时只能保存在自己的安全私人存储，不进入仓库/聊天/截图。退出本项目时先关闭 MITM，再删除设备中的对应描述文件并关闭信任。

证书固定/HTTP/3/应用内协议可能让 HTTPS 响应脚本无效或导致连接失败；本项目不安装越狱、解锁证书固定或全域名解密模块。没有通过关闭 TLS 验证来兼容。遇到证书报错先关闭该模块并恢复原始请求。

## 快速恢复，不影响正常生活功能

- 登录/支付/收消息/播放/领券异常：先把“广告拦截”改 DIRECT；仍异常则关闭相关 HTTP 覆写及 MITM，重建连接。
- 恢复后先只启用基础包；在最近连接找明确误杀域名，加入本机精确白名单，再试扩展包。
- 域名白名单只调整路由；若问题来自HTTP重写或JSON修改，需要关对应覆写。不要直接把整个支付主域纳入 MITM 或把整个 App 的所有请求交给陌生脚本。
- 无法定位时，退回上次在本机验收通过的公共覆写；不要删除私人订阅或账号资料。

本项目脚本不调用 `$httpClient`、不写存储、不推送通知、只输出固定诊断标记，不输出 URL/请求头/响应体；响应修改遇到大响应或未知结构直接放行。脚本自身的重复执行测试只保证广告转换幂等，**不代表签到每日去重已实现**。
