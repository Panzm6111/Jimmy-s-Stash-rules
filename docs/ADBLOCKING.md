## 已安装用户怎么更新

1. 保留已能用的配置备份、原本机私人订阅覆写和地区选择，**不重填机场URL、不重建私人覆写、不重装证书**。
2. 如果另装过“广告增强”、单独App广告覆写、expanded或临时诊断覆写，先停用这些额外广告条目，避免重复挂载。没装过就跳过；保留私人订阅覆写。
3. 在配置列表刷新原`config/stash.yaml`链接，选中它。配置文本开头应有`AD-20261020.5`；原18个策略组、DNS和私人“机场”provider保留，App专项及脚本URL声明已整合在主配置里。
4. HTTP/MITM保持开启，沿用已有完全信任的自建CA，断开并重新连接Stash。核对节点、地区选择和私人覆写关联。
5. 按[手机验收](PHONE-CHECKLIST.md)多轮测试冷启动、后台返回、触发预加载后再启动，同时检查登录、搜索、消息、视频和正常领券。

**日常只维护同一个公共主配置。** 无需逐款添加广告覆写或导入expanded。新增主机、原生动作、handler和脚本URL声明随主配置一起更新。11份响应脚本和1份手动自检脚本由Stash联网加载，配置24小时尝试刷新；URL增加版本参数以区分新版资源请求，不生成重复JS路径。仅刷新JS不能取得新主机或handler，也不保证原生缓存必然更新成功。建议扩展广告规则集每24小时自动尝试刷新，公共主配置每周手动刷新一次，修复发布后立即刷新；具体机制与机场更新统一见[更新教程](UPDATES.md)。

开发检查：最终配置应有一次`RULE-SET,基础广告,广告拦截`，provider URL指向`rules/vendor/ads-expanded.yaml`；保留局域网/系统例外优先级。主配置包含`http.url-rewrite`、响应handler及非空`script-providers.url`，没有旧`http.rewrite`或共享空响应provider。结构正确仍不等于Stash真机执行通过。

## 证书、规则与整体暂停的关系

域名规则只看连接目的，不需要解密。HTTP URL重写/响应脚本处理HTTPS时需要精确MITM主机和设备自建可信CA；CA只提供解密能力，不包含去广告规则。脚本只改已知路径，但解密范围是列出的整个主机；不添加通配支付/银行解密。

首次需要证书时，在Stash生成自己的CA并安装，iOS“设置→通用→关于本机→证书信任设置”开启完全信任，再设置HTTP/MITM。已经完成的不重复重装。私钥不进入GitHub、日志或聊天。不通过关闭TLS验证解决问题。

- 当前整合入口：已包含现有专项，按新需求不提供逐App开关。关闭额外同名覆写不能撤销主配置内置处理。
- 关闭域名拦截：广告组切DIRECT。**不会停止HTTP重写/脚本。**
- 暂停全部HTTP处理：在Stash界面关闭HTTP/MITM并重建连接；域名规则仍可工作。恢复时重新开启，不必重新安装证书。
- 旧本地包的“广告增强”不与当前整合入口叠加；旧文件仅用于兼容和静态交付。

## 不改YAML的15分钟排查

1. 更新原公共配置至`AD-20261020.5`，选中后重新连接Stash，原私人覆写与已信任证书保持不变。
2. 在Safari打开 **<https://example.com/jimmy-stash-check>**。应看到本机自检页面及脚本版本；如果看到普通Example Domain页面、404、证书错误或打不开，只反馈这一现象，不需要反复安装证书。
3. 点“开始15分钟诊断”，再进入页面上的结果页。开始链接用于新建一轮记录，查看结果时使用不带`?start=1`的原地址，避免重新开始覆盖本轮记录。
4. 完全关闭后打开淘宝、小红书等有问题的App，正常使用后回到Safari结果页刷新。记录广告是否仍在，同时看App模块的版本和固定状态。
5. 只反馈页面显示的App、版本和状态，以及广告位置。之后点停止，或等15分钟到期；停止后不再新增本轮记录。

页面显示实际请求使用HTTP还是HTTPS。**HTTPS自检成功只证明`example.com`这次请求进入HTTP脚本和MITM，不证明淘宝等App主机也命中。** 自检脚本只在手动访问上述精确路径时返回页面；为此新增`example.com`精确MITM主机。MITM范围是整个该主机的HTTPS连接，处理脚本仅限该路径；不增加App通配主机或银行支付解密。

开始后，11份响应脚本将模块版本、时间和固定状态计数写入Stash本机的项目专用存储；不会保存完整URL、参数、请求头、Cookie、Authorization、账号值或正文。未开始时不写诊断记录、不输出日志；页面与记录逻辑不向服务器上传数据、不发通知。计数用于观察执行分支，并非精确流量统计，并发执行可能覆盖部分计数。旧轮次不混入新轮次，停止或过期不代表已删除原有固定状态记录。

| 页面状态/固定代码 | 能说明什么 | 不能直接得出的结论 |
|---|---|---|
| 已产生修改 / `changed` | 脚本识别了已知结构，并把修改后的正文交给Stash | 不证明App采用了该响应或开屏已经消失 |
| 已识别、无需修改 / `unchanged` | 本次已知结构没有需要改变的内容 | 不证明其他广告接口也被覆盖 |
| 响应结构不支持 / `unsupported-schema` | 脚本执行了，但没有识别为支持的广告结构 | 不能删掉保护后盲改正常业务 |
| 正文不可用 / `body-unavailable`、正文过大 / `body-too-large` | 脚本进入，但没有可处理的字符串正文或超过限制 | 不能反推证书一定有问题 |
| 非JSON / `non-json`、JSON解析失败 / `parse-error` | 已取得字符串，但不是支持的JSON正文 | 不打印原始正文来排查 |
| 方法/状态不支持、HTTP错误 / `unsupported-method`、`unsupported-status`、`http-error` | 宿主字段或响应状态与当前处理条件不符 | 尚需区分真实宿主约定与服务返回错误 |
| URL未匹配 / `url-unmatched`、异常 / `exception` | 脚本内的匹配或执行没有正常完成 | 不等于已确认某个唯一根因 |
| 没有本轮记录 | 没有取得该响应脚本的本轮执行证据 | 可能没有新请求、路径未匹配、资源没更新、协议未进入引擎或广告来自缓存；不能单独断言MITM失败 |

微博开屏等43条原生URL动作不经过响应脚本，因此**不会因原生动作命中就在页面出现对应开屏记录**；微博模块的响应记录对应话题/搜索/热搜/评论处理。原生动作是否命中、执行超时仍须看Stash本机记录。需要进一步诊断时再按具体结果取最少信息，不要求发送完整网络日志。

旧[只读探针](../modules/diagnostics/ads.stoverride)与`argument: diagnostic=1`固定日志仍保留给维护者做隔离检查，默认不启用，不是这次手机操作步骤。探针与正式HTTP动作的执行先后需要隔离对照，不能把它叠加后没有日志直接认定为MITM失效。

## 当前边界与恢复

淘宝通用cloudvideo与poplayer未泛化启用，独立天猫App未有可靠专项；微博未声称覆盖全部首页信息流；小红书仅明确赞助项，不删普通带货笔记；美团新增仍为外卖链路，不代表主App完整覆盖；京东正文内functionId或加密新结构未获证据。其余完整范围见[逐款表](AD-MODULES.md)。

HTTP/3当前不进入改写引擎；本轮未观察真实QUIC，因此不默认禁UDP、不凭h3主机名下结论。不强制全域解密、不关TLS验证。预加载或缓存广告可能不发新请求；先用App自带清缓存入口，不默认卸载。

每款多轮检查冷启动、后台返回、预载后再启动，记录广告、空白、倒计时和加载变化；同时测登录/搜索/消息/视频/正常领券。单次无广告不算通过。误伤先将广告组切DIRECT排查域名，再关闭HTTP/MITM排查改写；仍异常可切回设备上实际能用的备份，私人信息只保存在设备。当前不要求逐App启停，排障采用上述整体对照与精确白名单；旧兼容文件不作为新增安装步骤。
